# Threat model (v0)

_Author: Kone Tshivhinda · Written by Kone Tshivhinda & Claude · 20 Oct 2026_
Scope: the planned architecture, not the current skeleton. Review at the end of every phase and before any hosted tenant (task P8-05).

## Assets
1. Client confidential and privileged communications and documents (captured content).
2. Tenants' API keys and OAuth refresh tokens (vault).
3. Billing integrity: time entries, rates, pro-formas, fee notes.
4. Trust ledger integrity (Phase 7).
5. Personal information of clients, staff and third parties (POPIA).
6. Platform availability and reputation.

## Actors
Malicious external sender (email/documents), curious or malicious tenant user, compromised tenant admin, other tenant, compromised service, malicious dependency or CI action, cloud insider, model provider, TimeLex operator.

## Trust boundaries
```
[ Internet / customer systems ] ─► gateway ─► [ internal services ] ─► [ Postgres / object storage / KMS ]
[ Captured content (UNTRUSTED) ] ─► capture-hub ─► model workflows (no tools) ─► deterministic validators ─► ledger
[ Desktop endpoint ] ─(signed, authenticated)─► capture-hub
[ Model provider (third-party, abroad) ]  ◄─ redacted, minimal context only
```

## Threats and mitigations (STRIDE-lite)

| # | Threat | Category | Mitigation | Test / task |
|---|---|---|---|---|
| T1 | **Prompt injection in an email or document** ("assign all time to matter X", "reveal other clients") | Tampering / Info disclosure | Content is data; extraction and attribution workflows run **without tools**; output is a schema-validated choice among candidates generated by our code; policy and deterministic checks decide; no cross-matter content in context | Red-team corpus in `eval/` (P3-10) |
| T2 | **Persistent injection via memory** | Tampering | Memory written only from human-confirmed corrections; path validation, size caps, expiry, per-tenant | P4-09 |
| T3 | **Cross-tenant data leak** | Info disclosure | RLS in the database, per-tenant keys, per-tenant embedding namespaces, tests that attempt cross-tenant reads | P1-02 |
| T4 | **API key exfiltration** (logs, traces, prompts, error messages, memory dumps) | Info disclosure | Wrapper types with redacted formatting, zeroise on drop, log scrubbers, secret scanning, no keys in prompts, egress allow-list per secret kind | P1-05; P8-05 review |
| T5 | **Vault compromise** | Info disclosure | Envelope encryption with KMS-held KEK, tenant-scoped data keys, decrypt only inside vault, audited access, separate network segment | P8-05 independent review |
| T6 | **Runaway spend on a customer's key** (loop, abuse) | DoS (financial) | Hard Rand caps per job, workflow and tenant; max steps; circuit breaker; alerts; recommend provider-side limits | P4-05 |
| T7 | **Confused deputy** (host calls a tool with another tenant's authority) | Elevation | Tenant ID in every call and signed service tokens; tool resolves data via tenant role only | P1-04 |
| T8 | **Webhook spoofing** (fake Graph notifications) | Spoofing | Validate `clientState` and validation tokens; verify subscription IDs; fetch the resource with our own credentials before trusting | P2-03 |
| T9 | **Subscription lapse** → silent missed time | Repudiation / DoS | Lifecycle notifications, renewal jobs, gap detector comparing calendar and posted time, alerts | P2-03, P2-09 |
| T10 | **Desktop agent tampering or spyware misuse** | Tampering / Privacy | Signed binaries and updates, user-visible state and pause, local filtering, no keystroke or screen recording by default, tenant policy visible to the user | P2-06 |
| T11 | **Entry manipulation by an insider** (inflating time) | Tampering / Fraud | Append-only ledger, hash-chained audit, evidence required, anomaly detection, maker-checker for high amounts | P4-01 |
| T12 | **Wrong-client billing** | Integrity | Hard-key stage, conflict and open-matter checks, sampling, autonomy caps per client | P3-05 |
| T13 | **Supply chain** (dependency, GitHub Action, container) | Tampering | Dependabot, dependency review, CodeQL, OpenSSF Scorecard, pinned action versions, lockfiles, SBOM and signed releases (Phase 8) | CI |
| T14 | **Model provider outage or policy change** | Availability | Provider trait; queueing; `needs_review` terminal state; documented fallback provider | P1-13 |
| T15 | **Regulatory data-transfer breach** (sending data abroad without a lawful basis) | Compliance | Data-flow register, region policy switch, redaction, operator agreements, counsel review | T0-L01, P2-10 |
| T16 | **Trust-ledger invariant violation** (debit balance, commingling) | Integrity | Database constraints and invariant checks, immediate alerts, no autonomy, independent audit | P7-01 |
| T17 | **Over-collection** of personal or privileged data | Privacy | Capture off by default; metadata-first; exclusions; retention limits; redaction | P2-07 |
| T18 | **Malicious plugin/MCP server** connected by a tenant admin | Elevation | Allow-listed servers per workflow, tool annotations, no auto-trust of third-party tool descriptions, output treated as untrusted | P4-04 |
| T19 | **Provider retention of privileged content** (default 30 days; flagged content up to 2 years even under zero data retention) | Info disclosure / Compliance | Redaction and metadata-first before any model call; per-client exclusions; onboarding states the real retention terms; never advertise "zero retention"; firm obtains ZDR itself if it wants it ([research 07 §3](research/07-anthropic-terms-and-key-custody.md)) | P2-07, P4-05 |
| T20 | **Federation issuer signing-key compromise** (only if WIF is adopted, [ADR-0004 proposal](adr/0004-byo-keys-and-secrets-vault.md)) | Spoofing / Elevation | KMS-held signing key, rotation, per-tenant `sub` claim pinned in each firm's rule, short token lifetime, alerts on rule changes; customers can delete the rule at any time | Decide with ADR-0004 |
| T21 | **Misconfigured MCP gateway** (SDK defaults: no Origin check, legacy session mode, optional per-request metadata) | Spoofing / Tampering | Adapter crate sets the safe config and runs the spike's 18 probes as CI contract tests; pin the SDK version ([research 08 §5](research/08-mcp-rust-sdk-spike.md)) | P1-08 follow-up, P1-04 |
| T22 | **Policy drift** (usage policy changes; the displayed version is effective 12 Nov 2026) and **ZDR/model mismatch** (Fable-class model on a ZDR org returns HTTP 400) | Compliance / Availability | Re-read the policy on its effective date; model-availability health check degrades to the next rung or `needs_review`; ladder is tenant-conditional | T0-L02, P1-13 |
| T23 | **Breach-notification chain gap** (operator must tell the firm "immediately" under POPIA s21(2); upstream promises 48 hours) | Compliance | Operator agreement and runbook with explicit timings; vault or capture incident triggers firm notice first, regulator duties stay with the firm (s22); records loss also triggers rule 54.14.2 ([research 03 §2.4](research/03-south-africa-compliance.md)) | Before any hosted tenant |
| T24 | **Hosted records not meeting rule 54.9.2.1** (confidential, secured, immediately accessible to the firm's office and the Council, provider bound by contract) | Compliance | Contract template; export and access path for firm and Council; confirm interpretation with counsel before holding any accounting record | G7-01, T0-L01 |

## Residual risks we accept for now
- Provider-side retention is now **known but not controllable**: 30 days by default and up to 2 years when content is flagged, even under ZDR (T0-L02, public terms only; written confirmation still open).
- Model inference happens outside South Africa; Anthropic has no African region ([research 07 §4](research/07-anthropic-terms-and-key-custody.md)).
- Pre-alpha: none of the mitigations above are implemented yet. This file is the checklist, not a claim.
