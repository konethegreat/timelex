# ADR-0021: Idempotent capture, connector cursors and replay

Status: Accepted · Date: 2026-11-01 · Deciders: Kone Tshivhinda, Claude

Builds on [ADR-0006](0006-event-sourced-activity-and-ledger.md) (immutable activity events), [ADR-0011](0011-tenancy-enforcement-and-database-roles.md) (tenant transactions and per-service roles), [ADR-0014](0014-transactional-outbox.md) (append in the writer's transaction) and [P2-01](../../contracts/events/README.md) (event versioning rules). Implements P2-02.

## Context

Every capture source delivers at least once. A mail subscription is retried when the acknowledgement is lost, a desktop agent flushes after a sleep, a backfill restarts from where it stopped, and an operator re-runs a connector after fixing its configuration. The same signal therefore arrives twice, sometimes many times, and sometimes with the order shuffled by the source system.

The product cannot tolerate a duplicated signal: a duplicated email would become duplicated billable time, and correcting it after the fact means editing derived work. ADR-0006 says events are immutable, so the duplicate has to be refused at the door rather than cleaned up later. The rule also has to be true across service restarts and multiple instances, which rules out any in-memory set of seen ids.

The connector half has its own hazard. A connector reads a page from the source system and records a cursor saying how far it has read. If the events are stored and the cursor is not, the next run re-reads the page; harmless because storing is idempotent. If the cursor moves and an event from the page is lost, the event is gone forever. Only one of those two orders is safe, and only a transaction can promise it.

## Decision

1. **The id is a function of the signal, not of the delivery.** An activity event's `id` is `ae_` followed by 32 lowercase hex characters: the first 16 bytes of `SHA-256("timelex/activity-event/id/v1\0" || u32_be(len)||tenantId || u32_be(len)||source.system || u32_be(len)||source.sourceId || i64_be(startedAt in whole Unix seconds))`. The four inputs are the firm, the source system in its contract spelling, the source's own id for the signal, and the start instant. Kind, actor, subject, content, capture time and delivery time are deliberately outside the rule, so a corrected label or a later capture of the same signal keeps the same id.
2. **Length prefixes, a domain separator and a fixed layout.** Each variable-length part is length-prefixed so that moving a character from one field to the next cannot produce the same bytes. The domain string ends in NUL, which cannot occur in an input. The layout is fixed for every `1.x` event, so a future reader computes the same id; the rule and a golden digest are published in [`contracts/events/README.md`](../../contracts/events/README.md) and pinned by a test.
3. **The receiver recomputes the id and refuses a mismatch.** A sender posts the event with its `id`; the service recomputes the canonical id from the event's own fields and answers 400 if the two differ. This makes the id a claim the service can check, not an opaque key a buggy or hostile sender chooses. A sender cannot force two copies of one signal by inventing a second id.
4. **Existence is a primary key, not a lookup.** `capture.activity_events` has primary key `(tenant_id, id)` and the insert is `ON CONFLICT (tenant_id, id) DO NOTHING`. Zero affected rows means the signal was already stored: the service answers 200 with `created: false` and writes nothing. One affected row means a new event: it appends `activity.recorded` to the outbox in the same transaction (ADR-0014), so the stream contains one event per stored event and never describes one that was not stored. A second unique key on `(tenant_id, source_system, source_id, started_at)` is a second line of defence against two different ids naming the same signal.
5. **Events are write-once.** The `svc_capture` role has `SELECT, INSERT` on events and no `UPDATE` or `DELETE`; the tests assert both are refused. A correction is a new event that cites the earlier one (ADR-0006). The stored row also keeps the event's JSON envelope beside the indexed columns, so a later reader sees exactly what was accepted.
6. **A connector is one trait and one opaque cursor.** `Connector::fetch(cursor, limit)` returns a page of events and an optional `next` cursor, or an error classified as retryable (`Unavailable`) or permanent (`Invalid`). The cursor is opaque text; the runner never parses it. The connector name is stored per firm, so two firms and two connectors never share a position. A missing cursor means "start from the beginning".
7. **A page and its cursor commit together.** The runner validates the whole page (connector name, cursor bounds, every event) before writing, then inserts each event and saves the cursor in one tenant transaction. If anything fails, nothing is stored and the old cursor stands; the next run re-reads the same page. A page larger than the requested limit, or a `next` equal to the cursor it was given, is refused as `Invalid`, because either would hide events or loop forever.
8. **Replay is the same path from the beginning.** `replay(tenant, connector)` starts at `None`, drains pages like a normal run, and does not save a cursor. Because storing is idempotent, a replay after a bug fix fills the gaps without duplicating what was already there, and the connector's normal position is untouched.
9. **A page's events belong to one firm and one caller.** Every event must name the caller's firm and the caller, checked before storage. Connectors run inside the service with no user token and call the store's connector path; the public ingest route demands a `principal` token with `capture:write`. Neither path trusts a firm from the request body alone.

## Alternatives considered

- **A random id generated at insert.** It makes every delivery a new event, which is exactly the duplicate the product cannot tolerate. Rejected.
- **A hash of the whole event JSON.** A metadata correction, a redaction pass or a capture-time difference would change the id and produce a second copy of one signal. It also binds the id to fields the rule should ignore. Rejected.
- **An HMAC with a service secret.** The id would differ between instances with different secrets and would change when the secret rotates, so a rolling deploy would duplicate recent signals. A secret adds nothing: the inputs are not confidential, and idempotency needs a deterministic, public rule. Rejected.
- **Deduplicate in the outbox consumer.** By then the event is already stored and visible in the firm's feed; a consumer cannot undo it without editing history. Rejected.
- **An in-memory set of seen ids.** It forgets on restart and differs per instance, so the guarantee holds only until the next deploy. Rejected.
- **Delete-and-reinsert on duplicate.** It would need `UPDATE`/`DELETE` on immutable events and would let a later delivery rewrite what was stored. Rejected.
- **Move the cursor first, then store.** A crash between the two loses the page permanently. Rejected.
- **Store each event in its own transaction and advance the cursor at the end.** A failure mid-page stores some events and loses the rest when the cursor eventually moves; a retry could re-read, but a partial page followed by a crashed run can leave the cursor ahead of what was stored unless every event is tracked. One transaction for the page is simpler and strictly safe. Rejected.
- **Replay by deleting the cursor and re-running.** It would work only because storage is idempotent, but it would also move the connector's normal position backwards, so a later scheduled run would re-read pages that replay had already covered. Rejected in favour of a replay that touches no cursor.

## Consequences

- **The id rule is public and permanent for `1.x`.** A future major may define a new rule; a `1.x` reader must keep computing the `1.x` id. The golden digest in the id tests makes an accidental change fail CI.
- **Whole-second precision is part of the rule.** Two genuinely different signals that share a source id, a source system, a firm and a start second would collide. In practice a source id names one signal, so the collision cannot arise; a connector that cannot supply a stable source id must derive one.
- **A source that changes a signal's start time creates a new event.** That is correct: the start instant is part of what the event means. A sender that only corrects metadata keeps the id and must publish a correction event, because the stored event is immutable.
- **The store is the arbiter of newness.** A sender cannot tell from its own state whether an event is new, and does not need to; it may retry freely and read `created` in the answer.
- **Page size is a promise.** A connector that ignores the limit is refused rather than truncated, so a large mailbox cannot turn one request into an unbounded transaction. The runner defaults to 100 events per page.
- **One transaction per page bounds the blast radius.** A page that contains one invalid event stores nothing; the connector must fix the event or the configuration. This is deliberate, because a partially stored page followed by an advanced cursor is the failure this design exists to prevent.
- **Replay is cheap and safe.** It re-reads from the source, so it costs the source's API quota, but it never duplicates and never disturbs the live cursor. Operators can run it after an ingestion bug without coordinating with the connector's schedule.
- **Revisit** when a source cannot supply a stable id (the rule needs a documented derivation), when pages must exceed one transaction for size, or when a second major of the event schema changes what "the same signal" means.
